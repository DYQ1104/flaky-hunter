# 如何定位测试用例的顺序依赖污染源

> 基于 flaky-hunter 的实现整理。工具仓库内可用 `fh demo` 复现本文的完整流程。

## 1. 问题：顺序依赖为什么难查

顺序依赖（test pollution / order dependence）指：一个用例单独执行能通过，但放在完整测试套件里就失败。典型原因是前序用例修改了共享状态——全局变量、环境变量、缓存、数据库、临时文件、单例连接。

它比普通的随机 flaky 更难排查：

- 失败日志通常只显示断言不成立，看不出是谁改坏了状态。
- 失败位置固定，但真正的污染源可能在上百个前序用例中的任意一个。
- 重跑往往仍然失败，开发者容易误判为"真实 bug"，直接去改用例本身。

人工排查的做法通常是不断注释前序用例、反复跑全量，成本极高。flaky-hunter 把这个过程自动化成一组隔离实验。

## 2. 第一个坑：顺序依赖会被归类为 broken

按失败率分类时，顺序依赖用例在完整套件里 **100% 失败**，因此会被归为 `broken`，而不是 `flaky`。

如果定位逻辑只处理 `flaky` 排行榜，就会完全漏掉这类问题。因此工具的目标集合是：

```
定位目标 = 全部 flaky（按 score 降序） + 全部 broken（按失败次数降序）
```

这也意味着，`broken` 里的用例必须先回答一个问题：**它是自己真的坏了，还是被前序用例污染了？**

## 3. 判定：两次基线 probe

对每个目标用例执行两次额外 probe：

| 实验 | 执行内容 | 判定 |
|---|---|---|
| A | 只跑目标用例 | 失败 → 不是顺序依赖，停止 |
| B | 按原顺序跑「全部前序用例 + 目标用例」 | 通过 → 本次未复现，标记 INCONCLUSIVE |

只有当 **A 通过、B 失败** 时，才确认是顺序依赖。

这两次实验就是区分「真实缺陷」与「顺序污染」的分水岭。示例仓库中：

- `test_broken` 单独跑仍失败 → 真实缺陷，不定位。
- `test_order_victim` 单独跑通过、全量跑失败 → 命中，进入下一步。

## 4. 二分：找到最小失败前缀长度

确认顺序依赖后，问题变成：前序用例序列 `prefix` 中，从哪一段开始让目标用例失败？

假设污染是单调叠加的——加入更多前序用例不会让失败消失。于是在 `[0, len(prefix)]` 上二分：

```
lo = 0          # 空前缀，目标通过
hi = len(prefix) # 全长前缀，目标失败
while lo + 1 < hi:
    mid = (lo + hi) // 2
    if probe(prefix[:mid] + [target]) == 失败:
        hi = mid
    else:
        lo = mid
```

最终 `prefix[:hi]` 是一个能复现失败的前缀。复杂度是 `O(log n)` 次 probe，而不是逐个尝试。

## 5. 最小化：贪心剔除无关用例

二分得到的前缀通常仍包含大量无关用例。逐个尝试剔除：

```
blockers = prefix[:hi]
for t in blockers:
    if probe(blockers - {t} + [target]) 仍失败:
        blockers.remove(t)
```

如果去掉某个用例后目标仍然失败，说明它不是必需的污染源。由于 `hi` 已经是较小的前缀，这一步的成本通常是线性的、可接受的。

## 6. 复核：证据不稳定就降级

一次失败可能是巧合。默认再重复执行最终集合 2 次：

- 稳定失败 → `FOUND`，confidence = high。
- 结果不稳定 → `UNSTABLE_EVIDENCE`，结论降级并在报告中注明。
- probe 预算耗尽 → `PARTIAL`，保留已有证据供人工复核。

所有 probe 的「执行集合 + 结果」都会写入 JSON 的 `evidence` 数组，结论可追溯。

## 7. 关键工程细节

### 7.1 以目标用例的结果为准，而不是进程退出码

这是实现中最容易踩的坑。

probe 执行的是一个子集，子集里可能包含 `test_broken` 这类必然失败的用例，进程退出码一定非 0。如果按退出码判定，会把无关的失败用例误判成污染源。

正确做法：解析本轮报告，只取目标用例自身的 outcome：

- `passed` → 通过
- `failed` / `error` → 失败
- `skipped` 或报告中找不到目标 → `indeterminate`，不计入通过/失败

### 7.2 nodeid 映射

JUnit XML 只提供 `classname` + `name`，没有可执行的 nodeid。工具同时调用 `pytest --collect-only -q` 获取 nodeid，并建立映射：

```
tests/test_a.py::TestC::test_x  ->  tests.test_a.TestC::test_x
```

定位时再把 nodeid 解析成绝对路径，避免 rootdir 与 cwd 不一致导致"用例找不到"。

### 7.3 probe 预算

单目标默认 60 次 probe。预算不是性能优化，而是安全阀：防止在污染不单调、或测试本身极慢时无限试探。预算耗尽返回 `PARTIAL`，比给出一个不可信的最小集更好。

## 8. 案例：一次真实运行

`fh demo` 的内置仓库包含 6 个用例，其中：

- `test_order_polluter` 向环境变量写入 `FH_DEMO_STATE=dirty`。
- `test_order_victim` 断言该变量为默认值 `clean`。

10 轮执行后的定位结果：

```
LOCATED POLLUTERS
  tests/test_order_victim.py::test_read_shared_state
    status: FOUND  probes: 10  confidence: high
    <- tests/test_order_polluter.py::test_write_shared_state
    reproduce:
      python -m pytest -q tests/test_order_polluter.py::test_write_shared_state tests/test_order_victim.py::test_read_shared_state
```

从 5 个前序用例中定位到唯一污染源，共消耗 10 次 probe（2 次基线 + 二分 + 最小化 + 复核），并给出可直接复现的 pytest 命令。

## 9. 复杂度与局限

- **复杂度**：基线 2 次 + 二分 `O(log n)` + 最小化 `O(k)` + 复核常数次，`k` 为最小失败前缀长度。
- **单调性假设**：如果污染需要多个用例配合，或会被中间用例清理，二分可能找不到全局最小集。工具标注为 best-effort，并保留完整证据。
- **共享状态范围**：定位依赖"前序用例 + 目标"这一执行模型，无法覆盖跨进程、跨机器的污染。
- **仅 pytest 可定位**：分析层支持任意 JUnit XML，但按 nodeid 精确执行目前只实现了 pytest adapter。

## 10. 小结

顺序依赖定位可以拆成四个可验证的步骤：

1. 用基线 probe 区分"真实失败"与"顺序污染"；
2. 用二分把候选范围从 `n` 缩到 `log n`；
3. 用贪心最小化剔除无关用例；
4. 用复核和证据表保证结论可信。

真正让它工程可用的，不是二分本身，而是两个细节：**以目标用例的报告结果判定 probe**，以及**把每一步证据完整落盘**。
